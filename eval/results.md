## The most important result is not in that table

**These metrics have run-to-run variance as large as the differences between configurations.**

| Run | Config | recall | role correct | over-claim | What changed |
|---|---|---|---|---|---|
| 1 | A | 0.000 | 0.000 | n/a (metric broken) | baseline |
| 2 | B | 0.333 | 0.958 | n/a | matcher fixed; vendor and role extracted directly |
| 3 | C | 0.556 | 0.793 | 0.333 | page budget shared across queries |
| 4 | D | 0.444 | 0.808 | 0.333 | capability-present not emitted as deployed; budget 12→16 |
| 5 | **C again** | **0.444** | **0.739** | 0.333 | reverted to run 3's exact configuration |

Runs 3 and 5 are the same code. Recall differs by 0.112 and role correctness by 0.054. Search results move between runs, pages change, and extraction is not deterministic even at temperature 0 — so a single run of a configuration cannot support a claim about that configuration.

This matters because **I made exactly that mistake.** Run 4 scored lower than run 3 and I attributed the drop to the change I had made, with a specific mechanism. Run 5 shows identical code producing run 4's number. The change may have been harmful, harmless, or helpful; this evaluation cannot tell, and the earlier confident diagnosis was wrong to state.

### What is trustworthy here

**The three metrics that never moved.** Honest refusal held at 1.0, thin-band false positives at 0, and provenance violations at 0 across all five runs and 64+ findings each time. A number that is stable across five runs of changing code is measuring something real. Keogh's Crisps, Barry's Tea and Ballymaloe Foods returned nothing every single time — including the collision case where searching Barry's Tea surfaces a chatbot built for DPD, and the near-miss where Keogh's adopted a non-AI ERP system in 2019.

**Provenance violations of 0 is an invariant, not a score.** The evidence gate cannot emit a finding without complete provenance, so anything above zero would be a bug in the gate rather than a quality shortfall.

### What is not trustworthy

**Recall and role correctness, at this sample size.** Both range widely. Recall's *cause* is understood — domain-scoped queries consume the page budget before vendor case studies are reached — but the *effect size* of any fix is not measurable with one run per configuration.

**Over-claiming at 0.333 is stable and therefore real**, and it is the outstanding defect. One of three capability-present items is reported as deployed rather than undetermined. The cause is known: `asserts_current_use` conflates two different things — a third-party vendor capability whose activation here is unpublished, and a dated announcement the company made about its own system. Only the first should become undetermined. Fixing it needs a distinct signal from extraction, not a downstream reinterpretation, which run 4 attempted and could not verify.

## What this evaluation needs to be usable for tuning

1. **Repeated runs per configuration** with a variance estimate, or
2. **A frozen page cache** so retrieval is held constant and only the code varies.

Without one of those, this suite can confirm that the honesty controls work — which it does, convincingly — but cannot attribute a change in recall to a change in code. That is a real limitation of the measurement, stated rather than papered over.

## Not measured

**Whether a quoted passage genuinely supports its claim.** Using a model to grade another model's output establishes that the two agree, not that either is right. The structural half is enforced — a quote must appear verbatim in the fetched page or the finding does not ship — but the semantic half needs hand-sampling and is not claimed as a number.
